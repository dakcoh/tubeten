## AWS 운영 구조

**AWS Lightsail 단일 인스턴스**에서 Ubuntu와 Docker Compose로 운영했습니다. 서버와 네트워크를 한곳에서 관리하는 데 적합한 구성이었습니다. **2 vCPU · 8GB RAM · 160GB SSD** 안에서 조회, 수집, 저장에 쓰는 자원을 관리했습니다.

메인과 Shorts 도메인은 같은 Nginx Gateway로 연결했습니다. 데이터는 **30분마다 관측**하고, 공개 순위는 **매시간 발행**했습니다.

```mermaid
flowchart LR
    Visitor["브라우저 · 검색 크롤러"] --> Gateway
    Youtube["YouTube Data API"] --> Collector
    subgraph Lightsail["AWS Lightsail · 단일 호스트"]
        Gateway["Nginx Gateway · HTTPS"] --> Main["메인 Nuxt SSR ×2"]
        Gateway --> Shorts["Shorts Nuxt SSR ×1"]
        Gateway --> Api["Spring Boot API ×2"]
        Main --> Api
        Shorts --> Api
        Api --> Mysql[("MySQL 8")]
        Api --> Redis[("Redis 7")]
        Collector["수집·집계 Batch ×1"] --> Mysql
        Collector --> Redis
    end
```

| 운영 과제 | 구현과 선택 |
| :--- | :--- |
| **공개 접속** | Nginx가 메인·Shorts의 HTTPS 요청을 받고 화면과 API로 라우팅했습니다. MySQL·Redis·애플리케이션 포트는 Compose 내부 네트워크에 두었습니다. |
| **순차 배포** | API와 메인 Web은 각각 두 컨테이너로 운영했습니다. 한 대씩 교체하며 새 이미지 SHA와 상태 검사 결과를 확인했습니다. 이중화의 범위는 컨테이너 교체와 프로세스 장애입니다. 두 컨테이너가 같은 호스트와 DB를 공유하므로 호스트와 DB는 단일 장애점입니다. |
| **장애 대응** | 수집·집계 작업은 별도 프로세스로 실행하고, 외부 API 요청과 DB 저장의 동시성은 각각 제한했습니다. Redis 조회가 실패하면 공개 조회는 DB를 사용합니다. |
| **데이터 복구** | MySQL 논리 백업과 복원 검증을 운영 절차로 정리했습니다. Redis 조회 캐시는 DB를 바탕으로 재생성합니다. 앱 이미지 교체와 DB 스키마 변경은 별도 작업으로 다뤘습니다. |

### 검증한 변경을 운영에 반영하는 흐름

```text
GitHub Actions 품질 검사
  → 통과한 커밋 SHA를 체크아웃해 API·Web·Shorts·Batch 이미지 빌드
  → GHCR에 커밋 SHA 태그로 게시
  → Lightsail에서 버전을 지정해 이미지 pull 및 대상 컨테이너 순차 교체
  → 실행 이미지 SHA·상태 검사·외부 응답·최신 집계 시각 확인
```

**복구 기준** · 애플리케이션을 되돌릴 때 이전 이미지 SHA를 지정할 수 있게 했습니다. 스키마 변경이 포함된 버전은 이미지 교체에 앞서 호환성과 백업 복원 여부를 확인하는 절차를 마련했습니다.

## 데이터 수집과 순위

1. **수집** · YouTube Data API에서 후보 영상과 공개 통계를 가져옵니다. 영상 ID를 중복 제거하고 최대 50개씩 묶어 요청합니다.
2. **계산** · 최근 유효 구간과 2·4시간의 시간당 증가, 증가 흐름의 지속성, 좋아요·댓글 반응을 계산합니다. 영상 형식과 게시 후 경과가 같은 집단에서 특징의 백분위를 구하고, 표본이 작으면 전체 후보 분포를 섞어 극단값을 완화했습니다.
3. **저장과 발행** · 동일 회차의 순위와 계산 특징을 한 트랜잭션으로 저장한 뒤, 완전성을 검사한 회차를 공개했습니다. 트랜잭션 커밋 후 관련 캐시를 갱신하고, 동일한 계산 정책의 연속 회차끼리 순위 변동을 비교했습니다.
4. **화면과 검증** · 순위 산정은 최근 관측 구간을 사용합니다. 영상 상세는 선택 기간, 확보한 관측 범위, 마지막 관측 시각을 구분합니다. 데이터 누락과 측정값 0도 별도 상태로 표시했습니다.

국가 라벨은 **후보 영상의 수집 범위**를 뜻합니다. 조회수에는 원본 영상의 전체 공개 수치를 사용했습니다. Shorts 분류는 길이와 공개 메타데이터로 추정했으며, 별도 Shorts 리스트에는 목록 내 순위와 전체 영상 집계에서의 순위 변화를 각각 표시했습니다.

공개 회차를 발행한 뒤 6시간·24시간의 관측값을 라벨로 만들어 비교할 수 있게 했습니다. 이후 성장한 영상이 상위에 들어오는 정도는 Recall@K·NDCG@K로, 연속 회차의 목록 변동은 Rank Churn으로 확인했습니다. 계산 정책마다 버전을 기록해 같은 기간의 결과를 비교할 수 있도록 구성했습니다.

## 대표 설계 사례

### 시간 초과 뒤에도 끝나지 않는 배치

후보 수집이 시간 초과된 뒤에도 스레드가 남아 있었고, 같은 실행 큐를 쓰는 스냅샷과 순위 계산까지 지연됐습니다. 시간 초과 시점에 곧바로 실행 소유권을 해제하면, 다음 회차에서 기존 작업과 새 작업이 겹칠 수 있었습니다.

시간 초과가 발생하면 같은 그룹의 다음 작업을 새 실행 풀로 넘겼습니다. 실행 중인 작업의 가드와 DB 소유권은 실제 종료 시점에 해제하고, 큐에서 시작을 기다리는 작업은 시작 가드에서 취소했습니다. 저장 경로에서도 영상 ID와 수집 시각을 유일 키로 두어 같은 스냅샷을 다시 받아도 기존 값을 보존했습니다.

운영 Batch는 단일 인스턴스입니다. DB 소유권에 만료 시각을 두었으며 실행 중 갱신은 구현하지 않았습니다. 다중 인스턴스로 확장할 경우에는 만료 전에 소유권을 갱신하거나 작업을 분할하는 설계가 필요합니다.

### 공개 리포트 요약과 회원 전용 본문의 응답 경계

지난 주차의 목록은 누구나 탐색할 수 있고, 전문은 회원에게 제공해야 했습니다. 목록에서는 원고가 있는 리포트만 추려 관측 근거를 한 번에 조회했습니다. 저장된 순위와 관측 구간이 원고와 일치할 때 핵심 발견과 근거를 두 필드로 반환했습니다.

상세 API는 본문을 조회하기 전에 회원 세션을 확인합니다. 비회원이 이전 주차를 직접 호출하면 `401`을 반환하며, 상세 응답에는 `Cache-Control: private, no-store`를 적용했습니다. API 테스트에서 근거가 맞지 않는 요약의 생략과 비회원·회원 응답을 검증했고, 운영에서도 공개 목록과 비회원의 상세 접근 차단을 확인했습니다.
